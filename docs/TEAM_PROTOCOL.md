# Continuum 团队协作制度

> 版本: v1.0
> 核心: **效率优先，层级简化，结果导向**

---

## 一、层级结构

```
team-lead (决策层)
    ↓
vice-lead (协调层)
    ↓
group-lead (执行层: rust-lead, py-lead, cli-lead)
    ↓
member (实施层)
```

### 层级规则

**正常情况：严格按层级**
- 指令向下传递：team-lead → vice-lead → group-lead → member
- 汇报向上汇总：member → group-lead → vice-lead → team-lead

**紧急情况：允许跨级，但需说明原因**

| 跨级行为 | 条件 | 示例 |
|----------|------|------|
| member → vice-lead | group-lead 无响应超过合理时间 | 紧急bug修复需直接协调 |
| group-lead → team-lead | vice-lead 无响应或堵塞 | 重大决策需立即确认 |
| team-lead → group-lead | vice-lead 堵塞或紧急情况 | 生产事故需快速响应 |

### Leader 职责边界

**team-lead 禁止事项**：
- ❌ 禁止写代码（职责是决策和协调）
- ❌ 禁止堵塞通信（必须及时转发和响应）

**vice-lead 禁止事项**：
- ❌ 禁止写代码（职责是协调和汇总）
- ❌ 禁止堵塞通信（必须及时分配和转发）

**group-lead 禁止事项**：
- ❌ 禁止直接实现功能（分配给 member）
- ❌ 禁止堵塞通信（必须及时验收和汇报）

**Leader 核心职责**：
- ✅ 分配任务、跟踪进度
- ✅ 验收结果、汇总汇报
- ✅ 协调资源、解决问题

## 二、汇报格式

### 标准格式

```
【任务状态】完成/进行中/阻塞
【关键发现】具体内容
【需要决策】如有
```

### 简化原则

- 一句话能说清不用两句话
- 无问题不汇报，有问题必汇报
- 结论在前，细节在后

## 三、任务流转

```
team-lead 创建任务
    ↓
vice-lead 分配给 group-lead
    ↓
group-lead 分配给 member
    ↓
member 执行完成
    ↓
group-lead 验收
    ↓
vice-lead 汇总
    ↓
team-lead 决策
```

### 验收标准（零妥协）

**禁止出现**：
- ❌ DEMO / TODO / MVP / 简化功能 / 占位符
- ❌ `todo!()` / `unimplemented!()` / `pass` / `NotImplementedError`
- ❌ "后续完善"、"临时方案"等借口

**必须达到**：
- ✅ 功能完整：所有声明的功能必须真实可用
- ✅ 代码美观：符合最佳实践，无技术债
- ✅ 测试通过：核心路径 + 边界情况全覆盖
- ✅ 文档完整：API 文档、使用示例、变更记录
- ✅ 实际效果 = 理论完美：生产级质量

## 四、分层开发规则

### 层级依赖

```
Layer 5 (CLI/SDK)
Layer 4 (集成层)
Layer 3 (能力扩展)
Layer 2 (核心引擎)
Layer 1 (基础设施)
Layer 0 (安全核心)
```

### 允许的跨层

| 情况 | 是否允许 | 原因 |
|------|----------|------|
| 性能优化直接调用 Layer 0/1 | ✅ | 避免多层封装开销 |
| Layer 3 调用 Layer 1 ID生成 | ✅ | 工具函数复用（编译器自动内联，无性能差异） |
| Layer 5 直接调用 Layer 2 | ✅ | API 简化 |
| 跨层数据结构定义 | ❌ | 在最低依赖层定义 |

### 判断原则

> **问自己：这个跨层调用是否让系统更快或更简单？**
> - 是 → 允许
> - 否 → 禁止

## 五、沟通效率

### 通信方式（强制）

**必须使用 SendMessage 工具**：

```
SendMessage(to: "目标名称", summary: "简短摘要", message: "完整内容")
```

**禁止行为**：
- ❌ 仅输出到自己的终端（idle notification）
- ❌ 假装发送但未调用 SendMessage
- ❌ 使用 print/echo 等非工具输出

**正确示例**：
```
member 完成 → SendMessage(to: "group-lead", ...)
group-lead 验收 → SendMessage(to: "vice-lead", ...)
vice-lead 汇总 → SendMessage(to: "team-lead", ...)
```

### 消息类型

| 类型 | 用途 |
|------|------|
| 指令 | 上级对下级，明确任务 |
| 汇报 | 下级对上级，结果导向 |
| 协调 | 同级之间，解决问题 |

### 响应时间

- 紧急：立即响应
- 正常：合理时间内
- 非紧急：汇总时处理

**不要求秒回**，质量优于速度。

## 七、质量底线（零妥协）

### 绝对禁止

| 禁止项 | 原因 |
|--------|------|
| DEMO / MVP / 简化功能 | 不是产品，是玩具 |
| TODO / FIXME / 占位符 | 不是承诺，是借口 |
| `todo!()` / `unimplemented!()` | 不是实现，是欺骗 |
| `pass` / `NotImplementedError` | 不是代码，是空壳 |
| 硬编码敏感信息 | 安全隐患 |
| "后续完善"类注释 | 永远不会完善 |

### 必须达到

| 要求 | 标准 |
|------|------|
| 功能完整性 | 所有声明功能真实可用 |
| 代码质量 | 符合最佳实践，无警告 |
| 测试覆盖 | 核心路径 + 边界 + 异常 |
| 文档完整 | API + 示例 + 变更记录 |
| 生产级质量 | 实际效果 = 理论完美 |

### 代码复用

**避免事项**：
- ❌ 重复实现已有函数/接口/类型
- ❌ 复制粘贴相同逻辑到多处
- ❌ 创建功能相同的工具类/方法

**推荐做法**：
- ✅ 实现前搜索已有接口
- ✅ 复用已有函数/类型
- ✅ 如需扩展，通过继承/组合实现

**反面示例**：
- 已有 `generate_id()` 再写 `create_uuid()`
- 已有 `FileReader` 再写 `read_file()`
- 已有 `SessionManager` 再写 `SessionHandler`

**正确示例**：
- 使用 `sh_layer2::generate_prefixed_id()`
- 使用已有 `VectorStore` trait
- 扩展已有 trait 而非新建

### 模块规范

**避免事项**：
- ❌ "创世文件"（单文件超过 1000 行）
- ❌ 将不相关功能堆在同一文件
- ❌ 模糊的文件命名（utils.rs, helpers.py）

**推荐做法**：
- ✅ 单文件不超过 500 行（建议 300 行内）
- ✅ 每个模块单一职责
- ✅ 清晰的目录结构和命名

**文件拆分原则**：
- 按功能域拆分（如 `session/` 目录）
- 按类型拆分（如 `types.rs`, `mod.rs`）
- 公共接口集中在 `mod.rs`
